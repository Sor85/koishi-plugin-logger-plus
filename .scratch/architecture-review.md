# 架构评审 — deepening opportunities

评审日期 2026-09-09，基线 `e3c7832`（4 753 行源码、92 条测试全绿）。

本文件是候选清单的落点：各 spec 与工单里出现的「候选 N」一律指向此处的编号。词汇沿用 `codebase-design` 的术语（module / interface / implementation / depth / seam / adapter / leverage / locality）。

> 评审结论的一句话概括：底层 module 大多已经很 deep（筛选编译、日志文件清单、倒序流式读取、自绘滚动条都通过了删除测试），问题出在**把它们组装起来的那一层没有 module**——seam 放在了会泄漏的高度，驾驶协议漏给了调用方。

## 候选 1 — 把视口协调器收成一个 module

**强度** Strong · **依赖类别** local-substitutable · **状态** 进行中

涉及：日志列表组件的编排段、虚拟列表布局 module、暂停位置 module、日志视图源码守卫测试。

虚拟列表布局与暂停位置两个 module 的算法已经很 deep 且各有测试，但把它们编排起来的那段没有 module——它是日志列表组件里的五个私有变量加七个函数，没有 interface，因此没有 locality。滚动位置有四个写者，其中三个由一个模块私有布尔量临时裁决。约束文档里已写下的不变量「同一帧内只允许一处改滚动位置」散在七处手工维持，零覆盖。

**深化方向**：抽出 `LogViewport`，interface 为一个 window 加六个意图动词，seam 从「布局数学」上移到「钉住这个滚动容器」。

完整规格见 `.scratch/log-viewport/spec.md`。

## 候选 2 — 「日志会话」缺 module，seam 长在原始 RPC 上

**强度** Strong · **依赖类别** ports & adapters

涉及：插件入口的分页查询与规范化、日志页外壳、日志列表组件。

同一份 RPC 契约在三处各声明一遍返回类型；请求体在外壳与列表组件各拼一遍；中间还被拆成六个 prop 传下去再组装回去。父子各握一半游标。

已产出三处具体后果：

- **`hasMore` 在半路丢失**——外壳打第一页却不读它，列表组件的「还有更早」初值写死为真。第一页即到头时「查看更多消息」仍会亮着。
- **初始游标靠巧合对齐**——列表组件对该 prop 的侦听没有 `immediate`，挂载时的初始值被丢掉，靠手写模板字符串恰好等于服务端游标编码兜住（与候选 4 同源）。
- **重置只能靠销毁子组件**——父组件无法通过 prop 清空内部状态，只能用复合 `:key` 加自增计数器把整棵子树拆掉重挂。

**深化方向**：把查询与分页契约移进已经跨层共享的筛选 module，再抽 `LogSession` 承接「条件 + 第一页 + 后续页 + 实时流」这一个概念。

## 候选 3 — 读历史日志逻辑闭包在插件启动函数里

**强度** Strong · **依赖类别** in-process

涉及：插件入口的 `apply` 闭包、两个服务端测试文件。

读一页历史日志的逻辑写在启动函数内部，只经控制台事件监听器露出，因此它的 interface 实际上是「整个 Koishi 运行时」。两个测试文件各写了一套假运行时（假上下文、假控制台、假日志器、假节流器、临时目录、真写文件），连基准配置都已经漂移成两个值（一处 100 KB、一处 200 字节）；同一文件里还并存两套监听器构造方式。

**深化方向**：抽 `LogArchive` module，显式接收目录、文件清单、同步钩子与错误上报，返回 `readPage(query)`。所需的下层 module（文件清单、倒序读取、筛选编译）都已经足够 deep，缺的只是把它们组装起来的那一个。

只动服务端与测试，与前端各候选无冲突，可并行。

## 候选 4 — 「日志身份」三份实现，命名收口失败

**强度** Strong · **依赖类别** in-process

涉及：客户端日志记录 module、插件入口的游标编码、日志列表组件的翻页请求。

每条日志的唯一标识是「时间戳:序号」，被四处消费（渲染 key、虚拟列表条目标识、滚动锚点、分页游标），但生成它的代码写了三遍：客户端一份、服务端一份、列表组件翻页时又内联手写第三份。只有一处有测试锁住格式。

删除测试：删掉客户端那个函数，格式不会集中，因为它本来就没集中——这是失败的命名收口，不是杠杆。

**深化方向**：放进跨层共享的一侧（与候选 2 的查询契约同处），把编码与「比较先后」的解码规则放在一起。顺带消掉候选 2 里那条「初始游标靠巧合对齐」。

## 候选 5 — 删掉只有测试在用的筛选便利函数

**强度** Strong · **依赖类别** in-process

涉及：筛选 module、其测试。

筛选 module 里有个逐条匹配的便利函数，在服务端与客户端**零调用**——生产走的是「编译一次、复用到 N 条记录」那条路径。它身上挂了 20 条断言，而真正的生产路径只有 1 条。它做的恰好是同文件注释明确警告过的事：按记录重新编译一次。

删除测试：复杂度消失，不在任何调用方重现——纯粹的穿透。

**深化方向**：删掉该 export，20 条断言改成编译一次再对多条记录求值。这份清单里最小的一项。

## 候选 6 — 文本与筛选口径散成多份

**强度** Worth exploring · **依赖类别** in-process

涉及：筛选 module、日志列表组件、插件设置页。

去除 ANSI 颜色码的正则写了两遍（搜索一份、复制到剪贴板一份），按插件路径筛选写了三遍。设置页那份还自带一份「跨重启分界」判定，与列表组件里的同名概念是第二份实现。

**顺带发现的真 bug**：设置页那份手写循环从最后一条数到下标 1 就停，永远看不到下标 0 那条。某插件恰好只输出一条日志时，设置页的运行日志显示为空。

**深化方向**：两处都改为 import 已经跨层共享的筛选 module，设置页的手写循环换成编译后的判定函数，边界一并修掉。零新增 seam。

## 候选 7 — 客户端在别人的配置树里按名字找自己

**强度** Worth exploring · **依赖类别** ports & adapters

涉及：日志页外壳的两个递归遍历、插件入口的配置定义与数据服务。

插件自己的两个开关在服务端有正经的配置定义，客户端却要在控制台的全局配置树里按名字把自己找出来，为此写了第二个递归遍历，还得懂控制台的配置编码（`~` 前缀、`group:` 嵌套、`name:path` 键）。控制台改编码时两个遍历一起**静默失效**，开关悄悄回落默认值。

**深化方向**：让插件已有的数据服务把自身配置一并下发，删掉那个按名字找自己的遍历；剩下的遍历只负责把插件路径翻译成显示名。复用现成 seam，不新增。

## 候选 8 — 右键菜单与剪贴板混在滚动机器里

**强度** Speculative · **依赖类别** local-substitutable

涉及：日志列表组件的选区、菜单项、贴边收拢与剪贴板降级写入，约 110 行。

这段与滚动状态零共享，只用滚动容器判断选区归属，却插在滚动协调器中间。

删除测试：抽出去后剪贴板降级、选区归属、贴边收拢集中在一处——复杂度是集中，不是搬家。

**深化方向**：抽 `LogLineMenu`，interface 三项。它与候选 1 是同一份组件的两块，先做候选 1 会让这块的边界自然浮现。纯整理，不修 bug 也不解锁新功能，优先级最低。

## 对照 — 已经 deep、不要动的部分

| module | 为什么已经 deep |
| --- | --- |
| 筛选条件编译 | 一个函数藏下 ANSI 剥离、大小写归一、路径集合、匹配文本缓存；测试穿过 interface 断言命中与否 |
| 日志文件清单 | 三个方法挡住两个真实故障：序号分配不展开数组、过期清理不重跑；用「取走所有权」代替加锁 |
| 倒序流式读取 | 一个生成器藏下倒读、字节级切行、UTF-8 边界拼接、残行丢弃；峰值内存与文件大小和数量都无关 |
| 自绘滚动条 directive | interface 极小，implementation 含拖拽、隐藏、观察器；两个 adapter（日志列表、下拉菜单），真实 seam |

## 建议顺序

1. **候选 1** 先做——它是唯一一处「复杂度真实存在却完全没有 interface 承载」的地方，做完后候选 2 与候选 8 的边界会自己显出来。
2. **候选 4、5、6** 各自独立、代价极小，可随时穿插；候选 4 会消掉候选 2 里那条隐患。
3. **候选 3** 只动服务端与测试，可与前端工作并行，还能与候选 2 共用同一份查询契约。
4. **候选 2** 在候选 1 之后做，届时日志列表组件里剩下的分页那一坨才干净。
5. **候选 7、8** 收尾。
