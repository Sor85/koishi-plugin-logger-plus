# refactor：把日志视口协调逻辑收进 LogViewport module

Status: done

最终验收与流程偏差见 [verification.md](verification.md)。

## Problem Statement

日志页的滚动是这个插件里最容易出问题的一处：往上翻一页会跳、加载更早日志之后位置歪掉、从别的页面切回来跑到底部。这些毛病有一个共同根因——**「谁在什么时刻改滚动位置」没有单一执行者**。

滚动位置目前有四个写者：贴底、按锚点复位、按布局粗定位，以及自绘滚动条拖拽。前三个挤在日志列表组件内部，由一个模块私有布尔量临时裁决；这条裁决规则在项目约束文档里已经用文字写下（「同一帧内只允许一处改滚动位置：手动恢复位置期间要挡住逐帧的高度修正」），但代码里没有任何 module 承载它，它散在七处手工维持。

更麻烦的是这段编排**没有可调用的 interface，因此没有测试面**。日志视图的 26 个「测试」全部是读源码文件加正则匹配（39 次读文件、137 条正则断言，零次组件挂载），断言的是九百行单文件组件的源码文本：改个变量名会红，改错编排时序却可能是绿的。虚拟列表布局与暂停位置这两个纯 module 各有 11 条和 4 条测试且全绿，但真实 bug 的位置在**两者的编排上**，那里零覆盖。

结果是：每次动这段代码只能靠人工在浏览器里翻日志验证，而回归不会报错，只会「感觉不对」。

## Solution

把视口协调逻辑收进一个 **LogViewport** module：一个小 interface（8 个动作 + 3 项只读状态），背后藏下虚拟列表的全部驾驶协议、锚点的两阶段恢复、帧调度，以及「同一时刻只有一处改滚动位置」这条闸门。

核心是纯 TypeScript，通过一个四方法的 **ViewportHost** seam 与 DOM 隔开，因此可以用一个字面量对象充当假容器、由测试手动推进帧，在无 DOM 环境下驱动整套滚动行为并断言最终停在哪一行。项目现有的裸 `node --test` 测试栈不需要改动，也不引入 jsdom。

对用户而言：滚动跳动、位置歪掉、切回页面丢失位置这几类问题从此有可执行的回归护栏，而不是每次改完靠手动翻日志验证。

## User Stories

1. 作为查看日志的用户，我希望在追踪最新日志时新日志不断到来仍停在底部，以便无需手动滚动就能看到最新输出。
2. 作为查看日志的用户，我希望向上滚动后自动暂停追踪，以便阅读时不会被新日志推走。
3. 作为查看日志的用户，我希望暂停期间新日志继续到来时当前阅读位置纹丝不动，以便不会读到一半被顶走。
4. 作为查看日志的用户，我希望点击「查看更多消息」加载更早日志后视口里原来那条日志仍停在原处，以便前插的内容不会让我丢失阅读位置。
5. 作为查看日志的用户，我希望日志行首次被精确测量（正文换行、跨重启分隔行的留白）导致高度变化时视口内容不发生跳动。
6. 作为查看日志的用户，我希望调整浏览器窗口宽度导致日志换行结果全部变化时当前阅读位置保持不变。
7. 作为查看日志的用户，我希望点击「回到底部」按钮后立刻回到最新日志并恢复追踪。
8. 作为查看日志的用户，我希望在设置中开启「返回时保持暂停位置」后，离开日志页再返回能回到上次暂停的位置。
9. 作为查看日志的用户，我希望上次暂停位置那条日志即使已经滚出渲染窗口，返回时仍能准确回到它。
10. 作为查看日志的用户，我希望在十万条日志的规模下滚动依然流畅，视口外的行不参与渲染。
11. 作为查看日志的用户，我希望恢复位置的过程中不出现「先跳到一处再弹到另一处」的二次跳动。
12. 作为查看日志的用户，我希望拖动自绘滚动条时列表不抖动。
13. 作为查看日志的用户，我希望恢复位置失败时（锚点那条日志已被卸载）列表保持当前位置不动，而不是弹到顶部或底部。
14. 作为插件维护者，我希望所有改动滚动位置的行为都经过同一个入口，以便新增功能时不必猜「我这时候动会不会跟别人打架」。
15. 作为插件维护者，我希望「先取锚点、再改内容、再复位」这个顺序由 module 强制执行，以便调用方无法把顺序写反。
16. 作为插件维护者，我希望「同一时刻只有一处改滚动位置」这条约束有一条可执行的断言，而不是只写在约束文档里。
17. 作为插件维护者，我希望能在无 DOM 环境下驱动整套滚动行为并断言最终停在哪一行，以便这次以及以后的改动都有回归护栏。
18. 作为插件维护者，我希望测试断言的是行为而不是源码文本，以便重命名变量或拆分函数不会让测试变红。
19. 作为插件维护者，我希望虚拟列表的调用协议（先设清单再取窗口、窗口吃的是内容坐标而非滚动位置、渲染后才能量高度、只有宽度变化才丢弃实测高度）不再是调用方必须背下来的知识。
20. 作为插件维护者，我希望日志列表组件不再持有五个互相牵制的私有变量与七个互相调用的编排函数。
21. 作为插件维护者，我希望搬运与行为改动分在两个提交里，以便出现回归时能二分定位到底是搬坏了还是后续改坏了。
22. 作为插件维护者，我希望搬运那一步有既有测试当护栏，而不是靠人工逐行比对。
23. 作为插件维护者，我希望约束文档里那几条硬约束在代码里有对应的注释锚点，以便下一个人不必先读文档才敢改。
24. 作为插件维护者，我希望核心逻辑不引入 Vue，以便「核心与框架无关」这条边界由 import 关系直接可见，而不是靠纪律维持。
25. 作为插件维护者，我希望测试不必引入 jsdom 或 happy-dom，以便测试命令保持现在这套裸 `node --test`。
26. 作为插件维护者，我希望这次改动不牵动历史日志分页与右键菜单，以便 review 范围可控。
27. 作为插件维护者，我希望自绘滚动条这个 directive 保持通用、不反向依赖日志业务，以便下拉菜单等其它使用者不受影响。
28. 作为后续接手的 Agent，我希望滚动协调的全部知识集中在一个 module 里，以便读一处就能理解整条链路，而不必在四个 module 之间来回跳。
29. 作为后续接手的 Agent，我希望这个 module 的 interface 就是它的测试面，以便判断某个改动是否安全时只需看这一层。

## Implementation Decisions

### 新增 module

**LogViewport** —— 纯 TypeScript 核心，不引入 Vue。外加一层薄 composable 负责 ref 绑定、生命周期与调度注入。两者分文件，让「核心与框架无关」这条边界由 import 关系可见。

### seam：ViewportHost

核心通过一个四方法接口与 DOM 隔开。以下类型形状来自 grilling 过程中的定型，比散文更精确：

```ts
interface ViewportHost {
  // 滚动容器几何；容器不存在或已离开 DOM 时返回 undefined
  metrics(): {
    scrollTop: number
    clientHeight: number
    clientWidth: number
    scrollHeight: number
    // 占位容器相对滚动容器内边距盒的顶部偏移；
    // 「查看更多消息」按钮与顶部内边距都算在它前面
    contentTop: number
  } | undefined
  // 当前渲染出来的行：标识、实测高度、相对容器视口顶部的偏移
  lines(): Array<{ key: string; height: number; top: number }>
  scrollTo(scrollTop: number): void
  estimatedLineHeight(): number
}
```

关键决定：

- `isConnected` 判断折进 `metrics()` 返回 `undefined`，调用方不需要单独判断。
- `lines()` 一次性满足锚点捕获与锚点恢复两边的需求，**核心因此不认识 `data-log-key` 这个渲染约定**。这正是当前暂停位置 module 的病灶所在。
- 拒绝了「host 就是像 HTMLElement 的东西」这个更贴近现状的方案，因为它会把 DOM 查询语义留在核心里。
- 拒绝了「调用方每帧把测量结果喂进核心」，因为它把「什么时候该量」的决策又推回调用方，等于没搬。

### seam：LogViewport 对外 interface

```ts
interface LogViewport {
  setItems(keys: string[]): void
  handleScroll(): void
  handleResize(): void
  followLatest(): void
  // 把会前插内容的变更交给它执行：
  // 先取锚点 → 执行 change → 等 DOM 刷新 → 按锚点复位
  around(change: () => void | Promise<void>): Promise<void>
  capture(): LogAnchor | undefined
  restore(anchor?: LogAnchor): Promise<void>
  dispose(): void
}
// 只读状态经回调流出：window / isFollowing / isViewingLatest
```

关键决定：

- **前插用 `around(change)` 而不是 `capture()` / `restore()` 一对。** 锚点必须在数据变更之前取，交给 module 执行才能让调用方无法弄错顺序——顺序约束留在调用方正是当前的病灶。
- **拒绝了「让 `setItems` 自行判断是否前插」**：它拿到的已经是变更后的清单，此时视口内容早已移动，读到的是移动后的位置，修正等于没做。这与约束文档「改占位高度前先取锚点」一致。
- `capture()` / `restore()` 仍然保留，但只服务于跨页面往返（keep-alive）这一个场景。

### 调度注入

`schedule`（生产环境是 `requestAnimationFrame`）与 `flush`（生产环境是宿主的 DOM 更新刷新）作为构造参数由 composable 注入，测试传同步实现并手动推进帧。

理由：**闸门与调度必须在同一侧**。若把调度留在 composable，「同一时刻只有一处改滚动位置」这条不变量就没有单一执行者。也拒绝了「核心直接调全局 `requestAnimationFrame`、测试替换全局」——那样拿不到确定性的帧推进，闸门本身就没法可靠断言。

### 状态回传

核心接受一个 `onStateChange` 回调作为构造参数，窗口与两项追踪状态一起给出，且**只在真正变化时触发**（沿用现有「四字段全等则不更新」的去重逻辑）。拒绝了订阅/退订机制（多余）与「每帧主动读一次」（会绕过去重，把「窗口没变」也变成一次写入）。

### 既有 module 的去留

- **虚拟列表布局 module 保留**为独立 module 与独立测试，但改为只被 LogViewport 引用，不再对日志列表组件暴露。它通过了删除测试：二分定位、脏偏移只重算尾段、按标识保留实测高度都是真算法。它那个「仅供守卫测试断言缓存不无限增长」的方法留在它身上，但**不出现在 LogViewport 的 interface 上**。
- **暂停位置 module 并入 LogViewport 实现，文件删除。** 它没有通过删除测试：那二十行会搬进一个已经在做两阶段恢复的函数，复杂度是搬家而非集中。它的 4 条测试锁的前提是「所有行都在 DOM 里」，而虚拟滚动上线后这个前提已经不成立。

### 写进核心的五条不变量

1. 同一时刻只有一处改滚动位置；`around` 与 `restore` 执行期间挂起逐帧高度修正。
2. 实测高度写回之前必须先取锚点。
3. `contentTop` 是布局值；占位只能用内边距，不能用位移变换。
4. 只有容器宽度变化才丢弃实测高度，高度变化不丢。
5. 找不到锚点时不强行恢复，保持当前位置。

### 明确留在渲染层的三件事

- **自绘滚动条的拖拽写入不纳入闸门。** 用户主动滚动（含拖拽）即视为暂停追踪；拖拽本身不改变内容，因此不触发逐帧高度修正。让 directive 反向依赖业务 module 会破坏它的通用性——下拉菜单也在用它。
- **跨重启分隔行的判定留在渲染层。** 分隔行的额外留白用内边距而非外边距（约束文档专门要求过），因此已计入实测高度，LogViewport 不需要知道哪行特殊。这也是判断该不该搬的硬标准：如果它需要知道，说明留白没进行高，那本身才是 bug。
- **原生滚动条宽度遮罩与「用户仍在查看」保活协议留在渲染层。** 前者是渲染细节，借 `onStateChange` 回调搭车更新；后者挂的是滚轮与指针按下事件，而 LogViewport 接管的是滚动事件，本就不冲突。

### 交付分两个提交

- **提交一（搬运）**：逻辑原样进入 LogViewport，日志列表组件改为调用它，**行为一行不改**。虚拟列表布局 module 与暂停位置 module **原样保留**并被核心引用。
- **提交二（补测试）**：新增行为安全网并跑绿，然后才把暂停位置 module 并入核心、删文件、删其测试。

## Testing Decisions

### 什么算好的测试

只断言外部可观察行为，不断言实现细节。本项目现状是这条原则的反面教材：日志视图的 26 个用例全部是读源码加正则匹配（39 次读文件、137 条正则断言、零次组件挂载），断言的是源码文本本身。它们既会被无害的重命名弄红，也可能在编排时序被改错时保持绿色——这不是测试，是源码快照。

### 被测 module 与驱动方式

被测 module 是 **LogViewport**，通过 **ViewportHost** seam 驱动。假 host 是一个字面量对象，维护滚动位置与行的几何；帧由测试手动推进而非等待真实 `requestAnimationFrame`。整个过程不触碰 DOM，不引入 jsdom 或 happy-dom。

### 8 条安全网

| # | 断言 | 现状 |
|---|---|---|
| 1 | 追踪时追加日志 → 滚动位置等于「总高度减视口高度」 | 无覆盖 |
| 2 | 向上滚 → 转入暂停；此后追加日志 → 滚动位置不变 | 无覆盖 |
| 3 | `around` 中前插 20 条 → 视口第一条的相对偏移与前插前相等 | 无覆盖 |
| 4 | 实测高度覆盖估算高度后 → 视口第一条的相对偏移不变 | 无覆盖 |
| 5 | 锚点滑出渲染窗口后 `restore` → 该行重新进入窗口且相对偏移等于原值 | 无覆盖 |
| 6 | 容器宽度变化 → 实测高度丢弃、总高度回落估算，且相对偏移不变 | 部分（只测了丢弃，没测位置） |
| 7 | `followLatest()` → 转入追踪且滚到底 | 无覆盖 |
| 8 | `around` 内部制造一次会触发高度修正的变化 → 全程 `host.scrollTo` **只被调用一次** | 无覆盖 |

第 8 条是「同一时刻只有一处改滚动位置」这条约束第一次拿到可执行的断言。第 3、4、5、8 条是这次改动最可能踩坏、且坏了不报错只会「感觉不对」的四条，恰好也全部无覆盖。

### 本仓库既有先例

- 暂停位置 module 的测试已经在用一个**非 HTMLElement 的字面量假容器**驱动真实函数并跑通。本次沿用并推广这个模式——区别在于新的假 host 是显式的 seam，而不是碰巧对上了实现所依赖的几个字段。
- 虚拟列表布局 module 的测试是纯算法测试的先例（含「十万条不展开数组」这条守卫），保持原样。

### 护栏策略

- **提交一不许改行为**：虚拟列表布局 module 的 11 条与暂停位置 module 的 4 条，共 15 条既有测试**一条不改、必须全绿**。这 15 条就是搬运期的护栏。
- 日志视图源码守卫测试里那 4 个滚动相关用例的正则改为指向新 module，暂时留任；提交二里安全网跑绿之后再删。
- **两条 CSS 守卫保留**：「占位不得使用位移变换」与「滚动容器必须自己充当定位父级」。它们防的是「有人写了不该写的 CSS」，本来就没有运行时行为可测，用正则表达是恰当的，且直接对应约束文档里的硬约束。

## Out of Scope

- 历史日志分页、`hasMore` 传递与游标归属（架构评审候选 2）。LogViewport 只提供 `around`，取数据的事仍留在调用方，因此改完后日志列表组件里仍会剩下分页那一坨。
- 右键复制菜单与剪贴板降级写入（候选 8）。
- 把自绘滚动条的拖拽写入纳入闸门。
- 插件设置页里那份独立的日志筛选实现。
- 引入 jsdom、happy-dom 或 Vue Test Utils。
- 日志身份三份实现的收口（候选 4）、去除 ANSI 口径两份实现（候选 6）、读历史日志逻辑从启动函数中抽离（候选 3）、客户端在配置树里按名字找自己（候选 7）、筛选便利函数删除（候选 5）。
