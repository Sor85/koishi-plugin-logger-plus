# refactor：把日志身份与游标语义收口为跨端共享 module

Status: ready-for-agent

## Problem Statement

一条日志由「时间戳加序号」构成的稳定标识，同时承担渲染标识、合并去重键、视口锚点和分页游标四种用途，其先后比较与游标编解码都基于它。但这套值语义目前有多份独立实现：客户端一份身份编码与内联排序，服务端一份格式相同的游标编码、一份先后比较、一份游标解析。客户端用身份编码生成游标发给服务端，服务端用另一份实现生成下一游标返回，两份必须逐字符对齐，全靠人工维持。

现有针对这套语义的测试大多是读源码文本匹配变量名与表达式：重命名会让测试变红，而客户端与服务端的格式一旦漂移却不会被发现。游标解析在非法输入下靠 `NaN` 比较偶然得到结果，这个行为没有被显式表达，也没有测试锁定。

## Solution

把日志身份的值语义收口为一个纯 module，客户端与服务端共享同一份实现。身份编码与游标编码成为同一个函数，记录先后比较与游标解析集中到一处，跨 JSON 边界的契约不再靠两份实现人工对齐。

用户可见行为不变：渲染标识、去重、视口锚点与分页结果都与现在一致，已发出的分页游标格式保持不变。维护者改动身份或游标规则时只改一处，并有直接的行为测试锁定，不再依赖源码字符串匹配或偶然的 `NaN` 比较。

## User Stories

1. 作为查看日志的用户，我希望同一条日志始终得到同一稳定标识，以便渲染、滚动锚点和去重都指向同一条记录。
2. 作为查看日志的用户，我希望实时与历史日志合并后不出现重复条目，以便不会把同一条日志看成两条。
3. 作为查看日志的用户，我希望合并后的日志保持稳定的时间先后顺序，以便连续阅读。
4. 作为查看日志的用户，我希望同一时间戳的多条日志按序号稳定排列，以便先后关系明确。
5. 作为查看日志的用户，我希望进程重启导致序号从头计数时，日志仍按时间戳主导排序，以便跨重启的先后正确。
6. 作为查看日志的用户，我希望客户端据以翻页的游标与服务端理解的游标是同一口径，以便翻页不重复也不遗漏。
7. 作为查看日志的用户，我希望服务端返回的下一游标能被客户端继续用于加载更早一页，以便分页连续。
8. 作为查看日志的用户，我希望缺失游标时从最新日志开始读取，以便首次加载得到最近记录。
9. 作为查看日志的用户，我希望非法游标不会意外返回全部历史，以便异常输入不放大读取量。
10. 作为查看日志的用户，我希望视口锚点使用的标识与渲染、分页用的标识一致，以便前插历史后仍停在原处。
11. 作为插件维护者，我希望日志身份的编码只有一处实现，以便客户端与服务端不会因各自维护而漂移。
12. 作为插件维护者，我希望身份编码与游标编码是同一个函数，以便二者天然一致而非靠约定对齐。
13. 作为插件维护者，我希望记录先后比较只有一处实现，以便合并排序与分页判定使用同一次序。
14. 作为插件维护者，我希望游标的解析与「是否早于游标」判定集中在一处，以便边界规则可读可测。
15. 作为插件维护者，我希望非法或缺失游标有显式判断，以便行为不再依赖 `NaN` 比较的偶然结果。
16. 作为插件维护者，我希望共享 module 不绑定客户端或服务端各自的日志记录类型，以便两端都能引用同一份实现。
17. 作为插件维护者，我希望合并去重、数组排序包装和记录截断仍留在各自原处、只消费共享语义，以便共享 module 只持有值语义本身。
18. 作为插件维护者，我希望针对身份、比较和游标的测试断言可观察行为而非源码文本，以便重命名或内部调整不会误伤测试。
19. 作为插件维护者，我希望有测试锁定客户端与服务端游标口径一致，以便跨端漂移能被发现。
20. 作为插件维护者，我希望已发出的分页游标格式在本次收口后保持不变，以便升级过程中翻页不失效。
21. 作为后续接手的维护者，我希望日志身份的全部规则集中在一个 module，以便读一处即可理解标识、先后与游标。
22. 作为后续接手的维护者，我希望这个 module 的 interface 就是它的测试面，以便判断某个身份或游标改动是否安全时只看这一层。

## Implementation Decisions

### 新增 module：日志身份

- 提取一个纯值语义 module，集中日志身份：身份编码、记录先后比较、游标编码与解析、以及「是否早于游标」判定。
- 身份编码与游标编码是同一个函数：客户端据以生成的游标与服务端理解、回传的游标因此天然同口径。
- module 使用结构类型（时间戳与序号两个字段），不依赖客户端或服务端各自的日志记录类型；沿用项目中「`src` 下的纯 module 被客户端跨目录 import 并同时供服务端使用」的既有先例。

### 值语义边界

- 收入共享 module：身份编码、记录先后比较、游标编码/解析、「是否早于游标」判定。
- 不收入：客户端的合并去重、记录截断，服务端的数组排序包装——它们是各自的行为，改为消费共享的身份与次序，不搬进共享 module。

### 游标格式与边界输入

- 保持现有游标 wire 格式不变，已发出的分页游标继续有效。
- 缺失游标表示从最新日志开始读取（维持现状）。
- 非法游标以显式判断处理，保持现有可观察结果（返回空页），不再依赖 `NaN` 比较的偶然行为，也不因异常输入返回全部历史。

### 两端接入

- 客户端身份与合并 module 改为消费共享 module 的身份编码与先后比较；渲染标识、视口锚点、去重与截断行为不变。
- 服务端日志归档改为消费共享 module 的身份/游标编码、先后比较、游标解析与「是否早于游标」判定；分页、筛选、早停与读取容错行为不变。
- 事件契约与返回结构不变。

## Testing Decisions

### 主要测试 seam

主要测试面是日志身份 module 的公开 interface。它是纯 in-process 值语义，测试直接调用并断言可观察结果，不挂载组件、不启动插件、不读源码文本。

### 行为覆盖

- 身份编码：同一记录得到同一标识；不同记录标识不同。
- 记录先后比较：同时间戳按序号排序；跨重启序号回绕时仍按时间戳主导。
- 游标编码与解析往返：编码后再解析回到同一身份。
- 「是否早于游标」：正确区分早于、等于与晚于游标的记录。
- 缺失游标从最新开始；非法游标得到明确的空结果，而非全部历史或报错。

### 既有测试的处置

- 客户端身份与合并 module 的既有行为测试保留，改为消费共享语义后仍绿。
- 服务端日志归档的既有游标与分页行为测试保留，改为消费共享语义后仍绿。
- 替换日志视图测试中锁定身份编码与渲染标识源码字符串、且已被共享 module 行为测试覆盖的断言。
- 两端调用同一函数，一致性由构造保证；保留一条断言编码格式稳定的测试即可，无需额外的跨端 diff 测试。

### 先例

项目现有裸 `node --test` 测试通过公开 interface 断言记录合并与服务端分页的可观察结果；日志身份测试沿用同一方式，只是被测对象换成集中后的值语义 module。

## Out of Scope

- 候选1（日志会话客户端编排）与候选2（日志归档服务端读取）已单独完成，不在本规格内。
- 分页生命周期、共享历史缓存、日期查询、历史读取与文件策略的行为变更。
- 游标 wire 格式、事件契约、排序方向与身份构成的变更（本次保持不变）。
- UI 外观、筛选算法、客户端展示逻辑的变更。
- 引入通用编码框架、可插拔序列化、UUID 或数据库主键等替代身份方案。
- 修改版本、许可证、发布配置或执行发布。

## Further Notes

- 本规格已在对话中经 grilling 逐项确认：共享 module 放在 `src` 且用结构类型、承载边界、`timestamp:id` 格式不变、非法游标显式处理、命名为「日志身份」、单张工单交付、不需要 ADR。
- 领域术语以 `CONTEXT.md` 为准，本 module 对应「日志身份」。
- 收益偏小且行为不变，价值在于消除跨端漂移风险与把源码字符串断言换成行为测试；这也是相较候选1、候选2评级更低的原因。
- depth 来自把身份、先后与游标编解码这套跨端值语义隐藏在一个 interface 后。删除该 module 会使这些规则重新散回客户端与服务端多处并再次依赖人工对齐；这是本次提升 locality 与 leverage 的验收依据。
- 本次为行为不变的收口：先完成提取并让两端既有测试原样跑绿当护栏，再补齐共享 module 的行为测试并替换相应源码字符串断言。
