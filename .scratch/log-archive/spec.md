# refactor：把历史日志读取提取为日志归档 module

Status: ready-for-agent

## Problem Statement

维护者想验证“给定查询，从已落盘日志读取一页”这一行为时，必须先启动整个 Koishi 插件、构造假 console、假 context、假 logger、假 throttle 和 dispose，再从注册的事件监听器里取出闭包间接调用。读取一页历史日志的实际 interface 因此变成了整个插件启动环境。

真正承载读取行为的逻辑闭包在插件启动函数内，与日志写入、文件滚动、过期清理、实时推送和生命周期共享局部状态。它已有覆盖不错的行为测试，但测试面处于错误高度：两份测试各自维护近似而不相同的假运行时，基准配置已经开始漂移。每新增一条读取规则，都要继续扩大这套假运行时，而不是只表达被测的读取行为。

## Solution

把已落盘历史日志的分页读取集中为日志归档 module，通过它自己的 interface 读取一页。插件启动只负责装配依赖，事件监听器降为把请求转交日志归档的薄 adapter。

维护者可以直接用真实临时目录驱动日志归档，断言分页、游标、筛选、排序、早停和文件竞态容错，不必再构造假 Koishi 运行时。用户可见行为不变：读取一页历史日志的结果、顺序、游标和是否还有更早记录都与现在一致。

## User Stories

1. 作为查看日志的用户，我希望按插件、等级、关键词或日期读取历史日志时结果与现在一致，以便重构不改变我看到的记录。
2. 作为查看日志的用户，我希望一页历史日志按从旧到新的稳定顺序返回，以便连续阅读。
3. 作为查看日志的用户，我希望同一时间戳的记录按既有次序稳定排列，以便跨重启的记录先后正确。
4. 作为查看日志的用户，我希望返回的游标能继续加载更早的一页，以便翻页不重复也不遗漏。
5. 作为查看日志的用户，我希望到达历史末尾时明确得知没有更多记录，以便知道查询已结束。
6. 作为查看日志的用户，我希望没有游标、没有日期、没有筛选时不触发磁盘读取，以便实时浏览不产生无谓的历史扫描。
7. 作为查看日志的用户，我希望非法日期条件返回空结果而非报错，以便异常输入不影响浏览。
8. 作为查看日志的用户，我希望读取历史前先把尚未落盘的最新日志刷入，以便刚产生的日志也能被读到。
9. 作为查看日志的用户，我希望单个日志文件读取失败时其余文件仍能组成一页，以便个别损坏文件不会让整页失败。
10. 作为查看日志的用户，我希望读取过程中文件恰好被清理删除时不产生任何日志，以便不触发写日志—滚动—清理的放大循环。
11. 作为查看日志的用户，我希望单日十万级文件规模下仍能读取一页，以便大量日志不导致崩溃。
12. 作为查看日志的用户，我希望凑够一页后立即停止读取更早文件，以便查询在大规模历史下依然快速。
13. 作为查看日志的用户，我希望关键词同时覆盖日志正文与插件名/标签命中的路径，以便保持现有搜索能力。
14. 作为查看日志的用户，我希望等级筛选只接受已知取值，以便前端传来的异常字符串不会把结果错误清空。
15. 作为插件维护者，我希望读取一页历史日志有独立于 Koishi 运行时的调用入口，以便测试不必启动整个插件。
16. 作为插件维护者，我希望通过日志归档的 interface 直接验证分页、游标、筛选、排序和早停，以便测试面处于正确高度。
17. 作为插件维护者，我希望用真实临时目录断言文件竞态和缺失文件的容错，以便这些硬约束有可执行护栏。
18. 作为插件维护者，我希望“读取前先同步写入”这条时序由日志归档强制执行，以便调用方无法漏掉它。
19. 作为插件维护者，我希望“什么错误该忽略”属于日志归档、“错误往哪报”由装配层注入，以便容错行为可测且不依赖全局日志器。
20. 作为插件维护者，我希望日志归档复用既有文件清单、倒序读取和筛选编译 module，以便不重复或拆散已经验证过的算法。
21. 作为插件维护者，我希望文件清单在写入与读取之间共享同一份，以便读取看到的文件与磁盘实际一致。
22. 作为插件维护者，我希望事件监听器只把请求转交日志归档，以便 Koishi 集成保持薄适配。
23. 作为插件维护者，我希望日志归档不认识 Koishi console 类型，以便读取逻辑与框架集成解耦。
24. 作为插件维护者，我希望插件启动函数不再承载读取一页的完整规则，以便读取相关的改动集中在一个 module。
25. 作为插件维护者，我希望本次提取不改变过期清理、文件滚动、写入和近期日志缓冲的所有权，以便重构范围可控。
26. 作为后续接手的维护者，我希望读取一页历史日志的全部知识集中在日志归档 module，以便读一处即可理解整条读取链路。
27. 作为后续接手的维护者，我希望日志归档的 interface 就是它的测试面，以便判断某个读取改动是否安全时只看这一层。

## Implementation Decisions

### 新增 module：日志归档

- 提取一个日志归档 module，集中已落盘历史日志的分页读取：查询规范化、游标判定、筛选编译、分页早停、排序、下一游标，以及读取前的写入同步与读取容错。
- module 核心不依赖 Koishi console 运行时类型；它组合既有文件清单、倒序读取和筛选编译 module，不拆解也不复制这些已验证的下层算法。
- 采用与现有服务端 module 一致的类形态，构造时接收依赖：日志目录、共享的文件清单、读取前的同步动作、以及非忽略错误的上报回调。

### interface 深度

- 对外只暴露“读取一页”这一个入口，输入沿用既有查询形态（游标字符串或含游标、日期与筛选条件的查询对象），返回沿用既有一页结果形态（记录数组、下一游标、是否还有更早记录）。
- 倒序流式读取生成器是 module 的内部 seam，只服务自身实现与测试推进，不进入对外 interface。

### 依赖与所有权

- 文件清单由插件启动函数持有并注入给日志归档；写入路径分配序号、跨日清理会修改它，读取路径只读取其倒序清单，双方必须看到同一份最新状态。
- 读取前的写入同步作为注入依赖，由日志归档在读取前调用；“读取前先同步”这条时序封在 module 内，装配层只提供同步的具体实现。
- 缺失文件（`ENOENT`）的静默判定属于日志归档；非忽略错误通过注入的上报回调交给装配层，由后者决定如何记录。
- 文件读取直接作用于真实文件，日志目录作为依赖传入；不额外抽象“记录来源”这一层，因为文件系统只有一个生产实现，测试用真实临时目录即可。

### 搬迁与适配

- 只服务读取一页的纯函数（查询规范化、筛选规范化、搜索路径规范化、日期校验、游标比较、游标编码、记录比较与排序）随日志归档一起迁移，保持读取相关知识的 locality。
- 一页读取的请求与结果类型定义随日志归档导出；Koishi console 的事件与 service 类型注册留在插件启动文件，引用日志归档导出的类型。
- 事件监听器降为薄 adapter，只把请求转交日志归档并返回其结果。
- 过期清理、文件滚动、日志写入、近期日志缓冲与最近日志读取仍属插件生命周期层，不迁入日志归档。

## Testing Decisions

### 主要测试 seam

主要测试面是日志归档 module 的“读取一页”interface。测试构造真实临时目录、注入共享文件清单、同步动作与上报回调，直接调用读取一页并断言可观察结果：返回的记录、顺序、游标、是否还有更早记录，以及缺失文件时的上报为空。测试不启动 Koishi 插件、不构造假 console/context/logger，也不断言私有状态或源码文本。

### 行为覆盖

- 按筛选与游标分页，返回记录、下一游标与是否还有更早记录。
- 单日十万级文件规模下仍能定位并读取一页，不展开大数组。
- 跨多个文件的分页顺序正确，倒序读取后恢复为从旧到新。
- 凑够一页后停止，不再打开更早文件。
- 等级与关键词组合筛选。
- 无游标、无日期、无筛选时不读取磁盘；非法日期返回空结果。
- 读取前完成写入同步。
- 单个文件读取失败时跳过该文件、其余文件仍组页；文件恰好被删除时不产生任何上报。

### 既有测试的处置

- 现有历史日志读取的行为测试改为直接驱动日志归档 module，保留其分页、大规模、跨文件、早停、筛选与文件竞态断言。
- 保留一条插件装配层的接线测试，证明事件监听器把请求转交日志归档并返回其结果。
- 过期清理的启动/跨日行为测试留在生命周期层，不迁入日志归档测试。
- 下层文件清单、倒序读取与筛选编译 module 的既有测试保留，不因本次提取删除。

### 先例

项目现有裸 `node --test` 测试通过公开 interface 与真实临时目录驱动服务端读取行为，并断言真实的一页结果与容错；日志归档测试沿用同一方式，只把入口从“启动整个插件后捕获监听器”换成“直接调用日志归档”。

## Out of Scope

- 候选1（日志会话客户端编排）已单独完成，不在本规格内。
- 候选3（跨端日志身份与游标语义收口）不在本规格内；本次不改变现有游标格式、身份与排序协议。
- 日志写入、文件滚动、过期清理所有权、近期日志缓冲与最近日志读取的行为变更。
- 页大小、单文件大小上限、磁盘文件格式、Koishi 权限与事件契约的变更。
- UI 外观、筛选算法本身、客户端展示逻辑的变更。
- 引入通用文件系统抽象、可替换记录来源或新的传输框架。
- 修改版本、许可证、发布配置或执行发布。

## Further Notes

- 本规格已在对话中经 grilling 逐项确认：文件清单共享注入、读取前同步注入、`ENOENT` 静默留 module + 上报注入、直读真实文件、只暴露“读取一页”入口、纯函数随 module 搬迁、Koishi 类型留装配层、单张工单交付、不需要 ADR。
- 领域术语以 `CONTEXT.md` 为准，本 module 对应“日志归档”。
- `CONSTRAINTS.md` 的日志文件规模约束继续有效：不展开大数组、流式早停、清理/读取遇缺失文件不写日志。这些约束在提取后必须仍由日志归档 module 保证，并有测试覆盖。
- depth 来自把读取一页的完整规则（含同步时序与容错策略）隐藏在一个 interface 后，而非给下层读取算法新增转发层。删除日志归档 module 会使这些规则重新散回插件启动函数，测试也重新依赖假运行时；这是本次提升 locality 与降低测试装配成本的验收依据。
- 本次为行为不变的提取：先完成提取并让现有装配层读取测试原样跑绿当搬运护栏，再把测试改写到日志归档 interface。
