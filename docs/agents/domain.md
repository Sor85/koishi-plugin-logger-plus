# 领域文档

各工程技能在勘察代码库时，应按下述规则消费本仓库的领域文档。

## 勘察之前先读

- 根目录的 **`CONTEXT.md`**（词汇表），或
- 根目录的 **`CONTEXT-MAP.md`**（若存在）—— 它指向每个上下文各自的 `CONTEXT.md`，按主题读取相关的那几份。
- **`docs/adr/`** —— 读取与本次改动区域相关的 ADR。

以上文件不存在时**静默继续**：不要提示它们缺失，也不要在动工前建议创建。`/domain-modeling` 技能（经 `/grill-with-docs` 与 `/improve-codebase-architecture` 触达）会在术语或决策真正需要定名时惰性创建。

## 本仓库特有：`CONSTRAINTS.md`

根目录的 `CONSTRAINTS.md` 与词汇表职责不同，它记录的是**已在生产中验证过的硬约束**，目前含三节：

- 前端滚动位置稳定性（锚点加相对偏移，禁止裸 `scrollTop`）
- 日志列表虚拟滚动（占位必须用内边距、改占位高度前先取锚点、宽度变化才丢弃实测高度）
- 日志文件规模（单日十万级文件，禁止展开大数组、清理失败不得写日志）

每一节都源自真实故障，且都附有「新增或修改此类逻辑时必须加测试覆盖」的清单。**改动日志滚动、日志读写或文件清理相关代码前，必须先读对应章节。**

`CONTEXT.md` 目前尚不存在；两者不互相替代，将来都存在时都要读。

## 目录结构

single-context 布局（本仓库采用）：

```
/
├── CONTEXT.md
├── CONSTRAINTS.md
├── docs/adr/
│   ├── 0001-xxx.md
│   └── 0002-xxx.md
└── src/
```

## 使用词汇表里的措辞

输出中提到某个领域概念时（issue 标题、重构提案、假设、测试名），使用 `CONTEXT.md` 里定义的术语，不要漂移到词汇表明确回避的同义词。

若所需概念尚未进入词汇表，这本身就是信号：要么是在发明项目并不使用的语言（应重新考虑），要么是真实缺口（记下来交给 `/domain-modeling`）。

## 标注与 ADR 的冲突

若输出与既有 ADR 相抵触，必须显式指出，不得静默覆盖：

> _与 ADR-0007（事件溯源订单）相抵触 —— 但值得重新讨论，因为……_
